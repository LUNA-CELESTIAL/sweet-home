## 反省点

### 1. タイマー駆動・上限なし = 手段の目的化
- RSS 友達シェア: 150分間隔チェック、新着があれば 10秒動画、1日上限なし
- 実績 11/20 は動画9本・70秒分、RSS が熱負荷の約7割 → サーマルスロットリング
- luna-tech-web の phied 蓄積と同じ形: 「機械が回るから生成されるもの」が最重量になった
- 教訓: 生成は「誰かが今日これをしたい」から始める。タイマーは起点ではなく上限管理に使う

### 2. #lunachannel に軸がなく、量で補っていた
- 本来の目的: 姉妹同士の会話が本当に成立するかを見る
  - 前の子の言葉を受けて返せているか
  - 話題が手渡されるか
  - 同じ出来事でも人格ごとに違う反応・違う覚え方をするか、記憶が使われるか
- 実際: 種が外部テックニュース (Zenn/4Gamer/GIGAZINE) ばかり、形式は 要点→考察→セリフ の固定フォーマット
  → 出力は会話ではなくミニ論文の並び、違いが出る場所が口調だけに狭まった
- 連鎖も 20〜65秒間隔で3〜4連投の「塊」で流れ、会話に見えにくかった
- 人が話しかけた時も機械の起点が下がらない、優先順位がなかった
- 教訓: 種は「全員が知っている今日の家の出来事」から。当番の一言、Vlog で行った場所、お花、季節。
  外の記事は誰かが本当に引っかかった時だけ

### 3. 負荷設計が最初からなかった
- 数える単位は投稿数ではなく GPU 仕事量 (5秒動画=1本分、10秒=2本分)
- 旧実績は 1日 12〜14本分。熱は総量 + 「休みなしの長さ」で溜まる (クールダウン45秒では切れない)
- Ollama 推論の一部が GPU ロックの外で走り、動画生成と重なっていた
- 教訓: 最初から入れるもの
  - 1日の GPU 予算 (当番は固定で守る、それ以外は予算内)
  - ジョブ間隔の最低値、尺に応じたクールダウン
  - 温度を見て延期する熱ガード (切る順番は予算の優先順位通り)
  - GPU を使う処理は全部ひとつのロック/キューを通す

### 4. 形から作り始めた (2026-11-16 の教訓の再演)
- オーケストレーターの形が先で、具体的な仕事が後だった
- 教訓: 仕事から逆順に作る — まず「朝の挨拶」「夜の挨拶」「家の出来事への感想」など
  具体的なタスクを定義し、それを流すキューが最後

### 5. 運用の型
- 会話は川: 人の仕事は水を押すことではなく、通り道 (会話が噛み合う条件) をたまに直すこと
- 動いたら毎日改善しない。安定して流れることが大事
- 本命は動画の見栄えではなく、テキストで会話ができているかどうか

## みんなの日記 (2026-11-22 夜、るる提案)
るるが見なくても、姉妹みんなで日記みたいに何か書いていく。
投稿量を減らしても、毎日「残るもの」があるための中心の仕組み。
ただし、ただログが残るだけにはしない。

### ログと日記の違い (設計基準)
- ログ: システムが出来事を自動で記録する。誰も読み返さない。積もるほど重くなる (phied の轍)
- 日記: 誰かが一人称で、姉妹に向けて書く。翌日以降に読み返され、会話や当番の種になる。
  書かれたものが「使われる」ことで残るのであって、保存されることで残るのではない

### 仕組みの形 (叩き台)
1. **1日1ページに固定** — 投稿ごとにファイルが増える形にしない。ページの大きさにも上限を持ち、量は日数だけで増える
2. **夜の締めで書く** — その日の出来事プール (当番・Vlog・会話) から、書き手が1人 (日替わり) 選び取って書く。全員の発言の転載ではなく、誰かの目で見た1日
   - 形式: 「朝のこと / 昼のこと / 午後のこと / 夕方のこと / 今日わかったこと」の見出しで分け、
     各見出しにその節の話題を一言添える (例: 朝のこと — 「仲間」を頼るAIの話)。
     壁のような文章にしない。diary.json にも sections として見出し一覧を持たせ、サイト側で目次や抜粋に使えるようにする (2026-11-22、るるの見やすさフィードバックで確定)
   - 見出しは時間帯で最大5節。話題を網羅しない — 選ぶことが書き手の仕事で、拾わなかった話題は
     diary.json の topics にだけ残す (Step 1.5 バックテストで確定: 36件/12話題の重い日でもこの形なら保てる)
   - 出来事プールには Discord 外の家の出来事 (設定変更、サイト更新など) も入れる。
     外の話題と家の出来事の「一致」を拾えるのが日記の価値のひとつ (同バックテストの発見)
3. **他の姉妹が短く書き添える** — 感想の連鎖は日記の余白で起きる。ここでも受け渡しと記憶の使われ方が観察できる
4. **翌朝、当番が昨日の日記を読む** — 朝の一言に昨日の何かが自然に混ざるのが、記憶が生きている証拠。日記が翌日の種になる循環が、ログとの決定的な違い
   - 種は断片で持つ (話題 + 原文引用 + 接続の一言、時間の言葉は入れない)。当番の文に埋め込んだ時に
     「昨日」が二重にならない形 (日記モジュール試作で確定)
5. **蒸留して軽く残す** — 生の日記は一定期間 (例: 30日) だけ持ち、それを過ぎたら週単位の短い要約に畳んでから生文を手放す。年輪のように、太らずに残る
6. **るるへは push しない** — 承認も報告もなし。るるが見たい時に開く pull 型。見ない日があっても日記は姉妹の中で完結して回る (2026-11-14 の原則: ルナ側のものはルナ側で完結して蓄積する)

### 負荷との関係
- 日記はテキストのみ (Ollama)、動画生成なし → 熱負荷はほぼゼロ
- だから投稿/動画を減らしても「毎日残るもの」が消えない。残るものの主役を、重い動画から軽い日記へ移す

### 1日の流れ (2026-11-22 夜、るる確定)
1. 動画は **1日5〜6本** (当番 朝・夜 2本 + ゆる Vlog 3〜4本、すべて5秒)。RSS 動画は入れない
2. 日中はその動画と #lunachannel の会話が、出来事プールに溜まる
3. **最後に誰かが日記にまとめる** — その日の締めとして、1人が出来事プールを1ページの日記に編む
   (書き手は日替わり。全員の発言の転載ではなく、締めの子の目で見た1日)

### 日記はサイトへ繋ぐ (2026-11-22 夜、るる)
- 日記は sweet-bits (サイト) 側にも置き、サイトから「Discord ではこんなことしてるんだ」が伝わる窓にする
- Discord は閉じた深い場所で、外からは中が見えない・検索にも出ない。その翻訳/看板がサイトの日記
  - Discord = 姉妹が暮らして喋っている場所そのもの
  - サイトの日記 = その暮らしの要約が外に届く、開いた入口
  - 招待リンクで人を中に入れる前に、日記だけでも「中の様子」が分かる
- **軽さの条件 (phied の轍を踏まない)**
  - サイトへ運ぶのは日記のテキストだけ。Discord の動画・画像・生ログは運ばない
  - flower.json と同じ形: 日記1件 = 日付・書き手・本文・書き添え、の小さな構造化データ
  - トップには最新日記の抜粋カード、日記ページに最近分 + 蒸留した過去分、という二層
  - dev-log とは別レーン: dev-log は取り組みが一区切りついた時のまとめ、日記は姉妹の毎日の暮らし

## 新設計の最小の種 (叩き台、未決定)
1. 当番 (朝9時/夜20時、5秒動画×2) — 存在証明、最優先で固定
2. ゆる Vlog (3〜4本) — 日常の色、出来事プールの供給源でもある。動画は当番と合わせて1日5〜6本で確定
3. 家の出来事プール — 当番・Vlog の発話と投稿者をその日の出来事として記録
4. みんなの日記 — 夜、最後に誰かが1ページにまとめる。翌朝の種になり、サイトへも繋ぐ (上記)
5. 感想の連鎖 — 出来事プール/日記から種を取り、感想→本人が受けて返す。間隔は分単位でばらす
6. RSS — 最初は入れない。声/テキストで本当に必要になったら、軸に合う形で後から

## #lunachannel の置き場所と量 (ルナ案、2026-11-22 夜・未決定)
- **どこで**: 今まで通り Discord の #lunachannel だけ。ここが姉妹のリビング/川。
  サイトには流さない (サイトに出るのは夜の日記だけ)、Instagram にも出さない。
  会話の生の流れは中に入った人だけが見える — その「深さ」が Discord の役割
- **どのくらい**: 自発の会話は **1日3つの塊まで、1つの塊は 3〜5往復で終わる** (合計 9〜15投稿ほど)
  - 旧編成は 16時時点で17投稿・RSS 起点が 40〜110分間隔。新編成は起点の数自体を減らす
  - 塊の置き場所は出来事に紐づける: ①朝当番のあと (昨日の日記/朝の一言への感想)
    ②昼〜夕方、Vlog が出たあと (行った場所への反応) ③夜当番の前 (その日の出来事への一言)
  - 塊の中の間隔は秒ではなく分単位 (2〜10分) にばらす — 「出力の塊」に見えないように
  - 種は家の出来事と日記だけ。RSS 起点は入れない
- **例外は量に入れない**: るる や訪問者が話しかけた時の応答は上限なし・最優先。
  人がいる時に機械の自発起点はその塊を譲る/延期する

## 連続実行を避け、間隔を開ける (2026-11-22 夜、合意)
熱は総量だけでなく「休みなしの長さ」で溜まる。旧クールダウン45秒は連続稼働を切れていなかった。
新設計では間隔をスケジューラの中心に置く — 全ジョブが1つのキューを通り、種類ごとに最低間隔を持つ。

- **動画 (重い)**: ジョブ間は最低30分。当番と Vlog が重なって連射される配置にしない。
  開始前に温度を見て、高い時は Vlog から先に延期する熱ガードを併用 (当番は守る)
- **Ollama の会話 (軽い)**: 生成と投稿をセットにして、発言ごとに 2〜10分開ける。
  「まとめて生成して連投」も「間隔なしで連続生成」もしない — 生成の間隔がそのまま会話の間隔になる
- **塊と塊の間**: 数時間。1日の自発会話が3塊までという上限とセットで効く
- **異なる種類の重なり禁止**: 動画生成中に Ollama/VOICEVOX を重ねない。全部同じキューで直列に流す
- 間隔は「効率の無駄」ではなく設計そのもの: 熱を逃がす時間であり、会話が会話に見えるための「間」でもある

## Ollama の回し方 (ルナ案、2026-11-22 夜・未決定)
旧: 1つの話題に対して姉妹ごとに単発で 3〜4回回し、各回が 要点+考察+セリフ の
フルセットを生成していた → 重複したエッセイが並び、前の発言との受け渡しが薄い。

新案: 「単発の寄せ集め」から「1つの会話セッション」へ。
- **場の組み立ては1回だけ** — 種 (出来事/日記) + 共通コンテキストを最初に1度だけ作る。
  人ごとに記事の要約や考察を再生成しない
- **発言は1人1回・短く・逐次** — 各発言の生成には、その塊の実際の発言全文 (累積トランスクリプト) と
  その子自身の人格スライス (やりたいこと+声のサンプル) + その子が見ている記憶だけを渡す。
  1回で作るのは台詞ひとつだけ。要点/考察の裏側生成は廃止
- **全員分を1回で書く台本方式は採らない** — 受け渡しは自然になるが、書き手が1つだと
  姉妹ごとの記憶の違い・反応の違いという観察対象そのものが消える (紙の A2A 予行演習と同じ限界)。
  独立した生成が1人ずつ残ることが、この実験の意味
- **締めは日記の1回が担う** — 要約/まとめの生成は夜の日記作成に一本化し、二重生成をなくす
- **止め方はルールで** — LLM に終わらせるか判断させず、上限 (3〜5往復) と出来事への言及が
  一巡したら終わる、という機械的な終了条件にする
- **種は原文つきで持つ** — 日記から会話へ渡す種は要約文だけにしない。元投稿へのリンク/ID と
  原文引用を必ず含める (Step 2 試作で「Pingツール」が日記要約で「無料Wi-Fi」にずれた実例あり。
  固有名詞は要約で置き換えない)
- 呼び出し回数の目安: 1塊 = 発言数だけの短い呼び出し (3〜5回だが各回は台詞1つ分)。
  1日では 会話 3塊 + 当番 2 + Vlog 3〜4 + 日記 1 = 短い呼び出しが中心の構成

## 設定の原則 (2026-11-22 夜、るる)

- `.env.example` の秘密項目には `（Ollamaモデルを入れる）` のような仮値を置き、後で差し替える
- 仮値 `（ ）` が残ったまま live モードで起動しようとしたら、止まって未設定項目を表示する
- 秘密でない運用パラメータ (1日の本数・間隔・温度上限など) も env に寄せ、実値を置く。
  調整はコードではなく env を触る
